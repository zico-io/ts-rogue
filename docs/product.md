# Product

## Shipped state

The repository contains a product plan, an engineering harness, and a runnable Ink shell that boots to a title screen, loads any existing save, and then routes into real Village, Overworld, and Dungeon scenes plus a real first-person Battle scene (turn-based combat, Phase 4), and an affix-driven loot system with monster-implicit pools that give players a reason to re-run specific dungeons (Phase 5).

The toolchain is in place: TypeScript, Vitest, and Biome on Node 24, with extensionless relative imports and Ink and rot.js as the locked runtime stack. `src/engine` holds the UI-free spine that later phases build on: a seeded RNG wrapper over rot.js (`src/engine/rng`), the serializable `GameState` with a pure reducer and store (`src/engine/state`), a party/economy data model (`src/engine/entities/party.ts`), an overworld generation/traversal module, a first-person dungeon module (`src/engine/world/overworld.ts`, `dungeon.ts`), and a turn-based combat module (`src/engine/combat`), and an affix-driven loot module (`src/engine/loot`). `GameState` carries `party` (an array of `PartyMember`, modeled as an array even though the milestone starts with a single hero, per PROJECT_PLAN §10), `gold`, `inventory` (owned, unequipped stacks of consumable items), `items` (owned, unequipped generated equipment instances), `nextItemId` (the monotonically increasing source of unique item instance ids), and `worldState` (the player's overworld position plus an encounter meter) alongside `seed`, `rngState`, `scene`, `log`, and `dungeonState` (the active dungeon run, or `null` until the party enters a dungeon entrance), plus `battleState` (the active battle, or `null` outside combat). `newGame` seeds a fresh run, creates one deterministic starting hero (`createStartingHero`), grants 50 starting gold, generates the overworld from the seed and starts the player on its village tile, and logs the seed into `GameState.log`; a `Log` event appends further messages immutably. `src/data/shops.ts` defines a static village shop catalog (`SHOP_ITEMS`) and the buy/sell price rule (`sellPriceFor`, half of buy price, rounded down); `src/data/dungeons.ts` defines deterministic dungeon chest loot (a pure function of the chest's floor and position, so saves agree without RNG); `src/data/monsters.ts` defines the monster roster (stats, first-person ASCII art, and XP/gold rewards) that Phase 4 battles read. Phase 5 extends `monsters.ts` with a `lootTableRef` and an optional `implicitPoolRef` per monster, and adds the loot data tables and engine module described below. The reducer (`src/engine/state/store.ts`) also understands `InnHeal` (fully heals the party for `party.length * INN_COST_PER_MEMBER` gold, no-op if unaffordable), `StoreBuy`, `StoreSell` (against the shop catalog and `gold`/`inventory`, no-op on unknown items or insufficient gold/quantity), `MoveOverworld` (which starts a battle when the overworld encounter meter crosses `ENCOUNTER_THRESHOLD`), the dungeon events `TurnDungeon`, `StepDungeon` (which starts a wandering or boss battle), `OpenChest`, `DescendStairs`, and the battle events `BattleAttack`, `BattleSkill`, `BattleItem`, `BattleDefend`, and `BattleFlee` (all delegated to the pure combat resolver in `src/engine/combat/resolution.ts`).

`src/engine/world/overworld.ts` generates a 42x21 biome tile grid (`grass`, `forest` passable; `mountain`, `water` impassable; plus `village` and `dungeonEntrance` waypoint tiles) as a pure function of `GameState.seed` (`generateOverworldMap`) - it is never duplicated into serialized state, only recomputed on demand, so identical seeds always yield identical maps. Generation scatters forest/mountain/water blobs onto a grass base, forces the village's immediate neighborhood walkable, then places three dungeon entrances only on tiles reachable on foot from the village (breadth-first search over passable tiles), guaranteeing the playable slice - walk from the village to a dungeon entrance - always exists. The `MoveOverworld` reducer case moves the player one tile: off-map or onto an impassable tile is a no-op (logged, no RNG consumed); onto the village or a dungeon entrance changes `scene` to `village`/`dungeon` directly; onto any other tile accumulates `worldState.encounterMeter` by that biome's danger (`biomeDanger`: grass 6, forest 14) times RNG jitter, and crossing `ENCOUNTER_THRESHOLD` (100) resets the meter and changes `scene` to `battle` ("A monster ambushes the party!"). Only successful moves consume the seeded RNG, so blocked moves are fully side-effect-free and the same seed plus move sequence always reproduces the same map and encounter outcomes.

`src/engine/world/dungeon.ts` generates a grid dungeon (rooms plus corridors via rot.js `Map.Digger`) as a pure function of `seed + dungeonId + floor`: it folds the three inputs into a single floor seed (an FNV-1a hash), saves and restores the global rot.js RNG singleton around `Digger` (which reads that singleton) and reseeds it with the floor seed, so the engine's serialized `rngState` stays untouched and identical inputs always yield an identical floor. Each floor fixes a 28x20 grid with a walled border ring, places the entrance at the first room's center, the stairs down at the farthest room's center on floors 1-2, the boss-room marker on floor 3, and one or two chests on random room floor tiles (via an independent seeded `Rng` wrapper). `createInitialDungeonState` builds the serializable `DungeonState` (floor, layout, player position plus an N/E/S/W facing, a Chebyshev-radius-3 explored mask, a pending-encounter flag, and a boss-reached flag) and reveals the area around the entrance. The dungeon reducer events are all pure `(state, event) => state`: `TurnDungeon` rotates the facing in place (no RNG, no log); `StepDungeon` steps forward or back, blocked by walls without consuming RNG, reveals the new area, rolls a 15% wandering encounter on plain-floor steps against the seeded RNG (starting a battle and flagging the encounter), and flags a fixed boss encounter plus `reachedBoss` when the party steps onto the boss marker; `OpenChest` grants deterministic loot (20-59 gold plus a Potion) and clears the chest feature; `DescendStairs` regenerates the next floor deterministically from `seed + dungeonId + (floor + 1)`; Both encounter kinds call `startBattle` (in `src/engine/combat/resolution.ts`), which consumes RNG to pick the enemy group and roll initiative and sets a fresh `battleState`; the battle events then resolve turn-based combat as described below. Stepping onto a dungeon entrance on the overworld (`MoveOverworld`) seeds `dungeonState` for floor 1 of that entrance's dungeon (`dungeonId = dungeon-${entranceIndex}`) and switches `scene` to `dungeon`.

`src/persistence/save.ts` exposes whole-state JSON `serialize`/`deserialize`, and persists a full `GameState` to a real single-slot sqlite database via Node's built-in `node:sqlite` (`saveGame`/`loadGame`, default path `./save.db`, upserted on every save; `loadGame` returns `undefined` before any save exists).

`pnpm game` runs the Ink shell (`src/app.tsx`) in the terminal's alternate screen, filling the current pane while the game is open and restoring the prior shell content on exit. `pnpm game:dev` starts the same game with a background developer console; backtick switches between the foreground game and console, which displays game logs and accepts `help`, `state`, `scene`, `log`, and `clear` commands. On boot it calls `loadGame()`: if a save exists, the `GameStore` starts from that state and the title screen reads "Press any key to continue"; otherwise it falls back to `newGame(Date.now())` and the title screen reads "Press any key to start". Either way, the first keypress only flips into the in-game router - it no longer unconditionally starts a fresh run, so a loaded save survives that keypress. Once started, number keys `1`-`4` dispatch `ChangeScene` to the village, overworld, dungeon, and battle screens (`src/ui/screens`); `q` or Ctrl+C exits.

Every gameplay and village scene renders through one shared frame, `src/ui/components/Screen.tsx`, so chrome and status placement are identical scene to scene: a full bordered panel that fills the pane with the scene title embedded in the top border edge, the scene's own content in a growing middle region, and a persistent footer. The footer is a `PartyBar` (one row per `state.party` member - name, level, HP colored green/yellow/red by remaining fraction, and MP - plus a gold line, scaling to the planned up-to-four-member party), an optional controls hint, and the shared `MessageLog`. Screens that place the log elsewhere (Battle pins it to the right of the combat layout) opt out of the footer log via `showLog={false}`. `Screen` owns the pane's height/width fill, so scenes no longer hand-roll their own title, party/gold status, or log. The `TitleScreen` and the developer console render outside this frame by design. The `MessageLog` (`src/ui/components/MessageLog.tsx`) keys each visible line by its absolute position in the log so repeated messages stay distinct; it shows the last `maxLines` (default 8) or, when given a fixed `height`/`width`, wraps to that box and shows only the lines that fit, so it never grows or spills.

The UI is fullscreen-aware and reflows to the live terminal size. `src/ui/hooks/useTerminalSize.ts` reads stdout columns/rows through Ink's `useStdout` and re-renders on resize (SIGWINCH), with safe 80x24 defaults for non-TTY/CI runs; `src/ui/components/MinSizeGuard.tsx` exposes that through a shared `TerminalLayoutProvider`/`useTerminalLayout` context (one resize subscription for the whole tree) and short-circuits every scene to a centered "Terminal too small" fallback below 64 columns by 24 rows. `Screen` reads that context, accounts for its own chrome (title line, border, footer) in one place, and publishes the remaining content region's fixed dimensions through `useScreenContent`; the responsive scenes size their viewports from it, so content only reflows when the pane resizes, never when the footer or a menu changes. The pure, UI-free render helpers take those dimensions and scale accordingly: the overworld camera viewport and downsampled minimap (`overworld/render.ts`), the dungeon first-person view (perspective-projected at the pane's native Braille dot resolution, `dungeon/render.ts`), and the battle enemy art, which greedily packs enemy columns into rows that fit the viewport width (`battle/render.ts`, `packEnemyColumns`). Each helper is unit-tested at several terminal sizes to assert scaling and packing without clipping or overflow.

The Village screen (`src/ui/screens/VillageScreen.tsx`) is real gameplay, not a placeholder: it shows the party's name/HP/MP and current gold, then lets the player pick a building or leave town with up/down + Enter or the `i`/`c`/`s`/`o` shortcuts, and `Esc` returns from a building to the overview.
- **Inn** (`src/ui/screens/village/InnView.tsx`) previews the rest cost as `party.length * INN_COST_PER_MEMBER` and dispatches `InnHeal` on Enter.
- **Church** (`src/ui/screens/village/ChurchView.tsx`) calls `saveGame(state)` on Enter (I/O lives in the UI layer, not the engine) and dispatches a `Log` event ("Game saved" or "Failed to save game") so the outcome shows in the shared message log. Loading only happens at boot, per PROJECT_PLAN §8.
- **Store** (`src/ui/screens/village/StoreView.tsx`) has two modes. Shop mode lists `SHOP_ITEMS` with buy price, `sellPriceFor` sell price, and owned quantity; up/down selects an item, `b`/`s` dispatch `StoreBuy`/`StoreSell` for one stackable unit at a time. Backpack mode lists the hero's equipped slots and generated loot (`state.items`) with rarity, stats, and a rarity/affix-scaled sell price; up/down selects, `e` equips (swapping the old item back to the backpack), `u` unequips, `s` sells, and a compare line shows the stat delta versus the slot the selected item would fill. Tab switches modes.
- **Leave town** dispatches `ChangeScene` to the overworld.

The Overworld screen (`src/ui/screens/OverworldScreen.tsx`) is also real gameplay: it renders a 21x11 camera-follow viewport centered on the player (clamped at the map edges) next to a bordered, downsampled minimap (3x3 tiles per cell, entrances always visible despite downsampling) built by the pure, UI-free helpers in `src/ui/screens/overworld/render.ts` (`buildViewportRows`, `buildMinimapRows`, `cameraOrigin`, `formatEncounterMeter`) and drawn with the shared `TileGrid` component. Tiles are glyphed as `.` grass, `%` forest, `^` mountain, `~` water, `H` village, `D` dungeon entrance, `@` player, each colored to match. Arrow keys or `h`/`j`/`k`/`l` dispatch `MoveOverworld`; `Esc` returns to the village directly as a convenience shortcut alongside the tile-based transitions. A text danger bar (`formatEncounterMeter`) shows the encounter meter as a percentage of `ENCOUNTER_THRESHOLD`.

The Dungeon screen (`src/ui/screens/DungeonScreen.tsx`) is real first-person gameplay, not a placeholder. The pure, UI-free helpers in `src/ui/screens/dungeon/render.ts` compose the view: `renderDungeonView` is a perspective wall-face renderer in the classic grid-crawler mold - every wall cell in view contributes its exterior faces, which are backface-culled, near-clipped, perspective-projected through a continuous camera pose (position plus yaw), and painted far-to-near as a magenta Braille wireframe onto the pane's native dot resolution, so side passages, corners, and doorways up to six tiles ahead render as the grid actually shows them; `renderMinimap` draws a 17x9 windowed top-down corner map (walls `#`, floor `.`, features by glyph, the party as its facing arrow `^>v<`, unexplored tiles blank) using the explored mask. Arrow keys or `w`/`a`/`s`/`d` (or `h`/`j`/`k`/`l`) turn and step the party; `o` opens the chest the party stands on; `>` or Enter descends the stairs the party stands on; `q` quits. The screen's content is the floor and dungeon id, the FP view next to a bordered minimap, and the party's facing; the shared `Screen` frame supplies the title, footer vitals, and message log.

The Battle screen (`src/ui/screens/BattleScreen.tsx`) is real first-person, turn-based combat (Phase 4, ROG-10), not a stub. The engine side lives in `src/engine/combat` (`types.ts`, `skills.ts`, `resolution.ts`), UI-free and pure: `startBattle` picks the enemy group and rolls initiative through the seeded `Rng`, and `resolveBattleEvent` resolves a full round per player command. `BattleState` (on `GameState.battleState`) holds the enemy group (each enemy's id/name/HP/stats and a copy of its first-person ASCII art facing the viewer), the fixed initiative order reused each round, an awaiting-command flag, the scene to return to, and a status of `ongoing`/`won`/`lost`/`fled`; hero HP/MP stay on `state.party` so a save never disagrees. Derived stats are pure and read effective stats (base stats plus equipped item bonuses), so `atkFrom`/`defFrom`/`spdFrom` = effective str / floor(effective vit/2) / effective agi; with no equipment equipped these equal the base stats, so prior combat behavior is unchanged. Damage is `max(1, floor((atk - def) * variance))` with variance in 0.85-1.15, crits (8% chance) at 1.5x, and a defending combatant taking half; hit chance is `clamp(0.9 + (spdAtk - spdDef)*0.02, 0.2, 0.99)`. Initiative is `spd + rng.next()*8`, ties breaking hero-first then by spawn order. The five actions are Attack, Skill/Spell (MP: Flame deals `floor((power+int)*variance)` ignoring defense; Heal restores `power+int`), Item (a Potion restores 30 HP, a Hi-Potion 99), Defend (halves incoming damage this round), and Flee (an RNG attempt vs the fastest living enemy, `clamp(0.55 + (spdHero - spdEnemy)*0.03, 0.1, 0.9)`; success ends the battle, failure yields the turn to the enemies). Each player command resolves the whole round in initiative order in one synchronous reducer step (the hero acts at their slot, each living enemy auto-attacks, and win/lose is re-checked after every action); a new round begins if the battle is still ongoing. Blocked commands (insufficient MP, no usable item, no living target) are fully side-effect-free and consume no RNG. Victory awards the enemies' XP and gold, applies level-ups, clears `battleState` and the dungeon encounter, and returns `scene` to the prior scene (`dungeon` for dungeon encounters, `overworld` for overworld); defeat revives the party at full HP/MP at the village, clears the dungeon run, and sets `scene` to `village` (permadeath is a later-phase decision). The level-up curve is exponential: `xpToNext(level) = floor(10 * 1.5^level)`; each level-up raises maxHp by 6, maxMp by 3, every stat by 1, and restores HP/MP to full, with `member.xp` tracking progress toward the next level and the remainder carried across. The Battle screen renders the enemy ASCII art facing the player with name/HP centered in a framed viewport, a floating command window titled with the acting member holding the selectable action menu with targeting (Up/Down + Enter, Esc to cancel), the hero's level/XP and derived ATK/DEF/SPD plus the initiative order below it, and the message log pinned to the right of the combat layout; HP/MP live in the shared footer vitals. Everything is driven from `state.battleState` and battle event dispatches. No UI snapshot tests exist, per PROJECT_PLAN §9; the combat math, level-up curve, initiative, a full win scenario, a full lose scenario, seeded determinism, and `battleState` JSON round-trip serializability are all asserted with exact outcomes in `src/engine/combat/resolution.test.ts`.

The loot system (Phase 5, ROG-11) is affix-driven and lives UI-free in `src/engine/loot` (`types.ts`, `affixes.ts`, `items.ts`, `resolution.ts`, `equipment.ts`) over static content in `src/data` (`itemBases.ts`, `affixes.ts`, `lootTables.ts`, `implicitPools.ts`). Drop resolution per kill and per chest follows a fixed order, every roll routed through the seeded `Rng` so a seed plus event history always reproduces the same drops: (1) a base-tier roll decides whether anything drops (`LootTable.dropChance`); (2) a weighted rarity roll picks common/magic/rare/unique; (3) a source pool is selected, with trash mobs rolling their tier's generic loot table while bosses and special enemy types also roll their monster-implicit pool; (4) affixes are generated, prefix/suffix counts capped per rarity (common none, magic 1/1, rare and unique up to 3/3) and values rolled within each affix's range, gated by the item base's item level so deeper content unlocks stronger affixes. Generated items are serializable `ItemInstance`s (base id, rarity, item level, rolled prefixes/suffixes, and an optional fixed implicit) with unique ids stamped from `GameState.nextItemId`. Monster-implicit pools give players a reason to re-run a specific dungeon: type pools (`type_...`, e.g. slime) attach to an enemy type and drop infrequently from any of that type across the world, while boss pools (`boss_...`, e.g. the dungeon guardian) attach to a unique boss and drop reliably, each signature item forcing a rarity and carrying a fixed signature implicit on top of its rolled affixes so the drop is recognizably that monster's. On victory the combat reducer rolls loot for every defeated enemy (a boss kill yields a generic drop from the boss table plus a signature drop from its implicit pool) and appends `Looted ...!` lines to the message log shown on the return scene; chests additionally roll a generated item from the floor's chest loot table on top of their deterministic gold and consumable. The store's Backpack mode equips, compares, and sells generated loot; selling refunds `itemSellPrice` = `floor(baseValue * rarity multiplier) + total affix value`, and equipping moves an instance between `state.items` and a party member's equipment slot. Because `items`, `nextItemId`, and equipped `ItemInstance`s are part of the single serializable `GameState`, a save round-trips all loot and equipment.

The repository also ships an Eve project agent under `agent/`. It receives work through Linear, uses Linear as its tracker, and runs repository tasks in Vercel Sandboxes pre-warmed with the repository and locked pnpm dependencies. Linear sessions show tool calls, delegation, reasoning, and rich Markdown progress from root or delegated work as native activities, and present approval prompts as native selections. Linear tools run without human approval, and progress stays in the Agent Session instead of issue comments. Eve uses `zai/glm-5.2` for root orchestration, performs a bounded orientation using the assigned Linear identifier and one batched repository read, then delegates ordinary implementation to one `deepseek/deepseek-v4-flash` coding child with a complete orientation packet. The child skips repeated global orientation and reads only task-relevant code. GitHub credentials are brokered through Vercel Connect and do not enter the sandbox; Eve uses `git` and the GitHub REST API directly instead of probing for credentials or creating test branches.

The intended playable loop, architecture, phases, and definition of done are maintained in [`PROJECT_PLAN.md`](../PROJECT_PLAN.md). Linear holds issue status, ownership, and priority.

## Documentation contract

This document describes shipped behavior only. Update it in the same pull request when product behavior changes. Update `README.md` when setup, commands, requirements, or top-level layout change.

`pnpm docs:check` validates local Markdown links. In pull requests, it also rejects changes to product code or runtime configuration that do not update `docs/product.md`.
